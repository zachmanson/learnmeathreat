## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Anchor hash scheme
- **D-01:** Heading IDs switch from today's rehype-slug text-derived slugs (e.g. `#why-shors-algorithm-breaks-ecdsa`) to **sequential numeric IDs** (`#h-1`, `#h-2`, ...). Chosen for maximum stability — the ID is position-based, so editing a heading's wording later never breaks a previously shared link. Trade-off accepted: the ID isn't self-descriptive from the URL alone.
- **D-02:** Numbering covers **all headings except h1** (h1 is the post title, not a section), in document order — h2 and h3 share one sequence rather than having separate counters. This matches how both sidebars will need to walk the heading tree.

#### Left sidebar — site-wide post navigation
- **D-03 (scope correction — important for downstream agents):** The left sidebar is **not** a per-page outline. It lists every post on the site, organized into chapters — it's the site's book-style table of contents. The right sidebar (below) is the per-page "on this page" outline. Do not conflate the two.
- **D-04:** Posts are grouped into chapters using their existing **freeform tag frontmatter** (`z.array(z.string())`, unchanged from Phase 1's D-04). Do **NOT** lock a fixed chapter/category enum in this phase. The user plans to tag their first posts under one chapter (e.g. "Bitcoin Fundamentals") and organically add more chapters as they write more posts — the sidebar must group dynamically off whatever tag values exist, not a hardcoded list.
- **D-05:** The left sidebar is **always visible on desktop** (above the ~900px breakpoint, see D-10), hidden behind a toggle control on mobile/tablet.
- **D-06:** Chapters are **accordion-style, individually collapsible/expandable**. The chapter containing the post currently being viewed starts **auto-expanded**; other chapters start collapsed.
- **D-07:** The left sidebar appears **only on individual post pages**, not on the homepage (which already lists all posts reverse-chronologically) or the About page.

#### Right sidebar — on-this-page outline with scroll-spy
- **D-08:** Shows the current post's own headings, **h2 + h3 nested** (fuller outline than the left sidebar's post-level grouping — useful for scroll-spy granularity in long posts).
- **D-09:** The active/in-view section is highlighted with **bold/accent-color text only** — no border or indicator bar. Matches the existing minimal aesthetic (Phase 2's quiet accent-color usage), avoids introducing new visual weight.
- **D-10:** The right sidebar **hides itself entirely** on posts with fewer than 2 headings (avoids showing a near-empty or single-item box).
- **D-11:** On mobile/narrow screens, the right sidebar is **hidden entirely** — no toggle (unlike the left sidebar). Rationale: avoids two competing toggle controls fighting for space on narrow screens.

#### Overall page layout
- **D-12:** On desktop, both sidebars **flank the existing centered content column** — the post content stays at its current 68ch width and page-centered position (`src/styles/global.css` `.site-header, main { max-width: 68ch; margin: 0 auto; }`); sidebars occupy the margin space outside it. This is a smaller change than shifting the whole three-column block off-center, and preserves Phase 1/2's established centered-column reading experience.
- **D-13:** The breakpoint that collapses to the current single-column mobile layout (hiding both sidebars, per D-05/D-11) is **~900px (tablet and below)** — sidebars only appear on genuinely wide desktop viewports where there's real margin space to use.

## Summary

The two riskiest-sounding parts of this phase — the custom sequential-numeric heading-ID scheme and getting a matching heading tree out of Astro for both sidebars — turn out to be low-risk once you understand Astro's internal pipeline order, which was verified directly by reading the installed `@astrojs/markdown-remark` source (`node_modules/@astrojs/markdown-remark/dist/index.js` and `rehype-collect-headings.js`), not just inferred from docs. Astro always appends its own internal heading-ID/heading-collector step (`rehypeHeadingIds`) **after** every plugin listed in `markdown.rehypePlugins`, and that internal step only assigns an id if `node.properties.id` is not already a string — otherwise it reuses whatever id is already on the node and pushes `{ depth, slug: <that id>, text }` into `file.data.astro.headings`, which is exactly what `render(post)` exposes as `{ Content, headings }`. So a custom rehype plugin that assigns `#h-1`, `#h-2`, ... in document order, placed anywhere in `markdown.rehypePlugins` before `rehype-autolink-headings`, automatically becomes the source of both the DOM `id` attributes *and* Astro's own `headings` metadata array — no separate heading-extraction mechanism is needed, and there is no id mismatch landmine as long as plugin order is respected.

The remaining pieces (site-wide left sidebar, per-page right sidebar with scroll-spy, collapsible accordion, 3-column layout) are all standard, low-dependency patterns: a `getCollection('posts')` query grouped by `tags[0]`-or-similar for the left sidebar, `render(post)`'s `headings` array (filtered to depth 2/3) for the right sidebar, a small IntersectionObserver-based scroll-spy script following the same "small inline script" shape as `ThemeToggle.astro`, and CSS Grid with three named columns (`nav-left content nav-right`) collapsing to a single stacked column via a media query at the agreed ~900px breakpoint — no restructuring of the existing `.site-header, main { max-width: 68ch; margin: 0 auto }` rule is required if the grid is applied to a new wrapper around `<main>`, not to `main` itself.

**Primary recommendation:** Replace `rehype-slug` with one small custom rehype plugin (`src/lib/rehype-sequential-ids.mjs`, ~15 lines, using `unist-util-visit`) that assigns `h-1`, `h-2`, ... to all `h2`-`h6` elements in document order; keep it ahead of `rehype-autolink-headings` in `markdown.rehypePlugins`; consume `render(post)`'s `headings` array (now carrying the custom ids) for both sidebars — no custom heading-extraction code needed beyond the id plugin itself.

### Pattern 1: Sequential heading-ID rehype plugin

**What:** A rehype plugin that walks the hast tree in document order, assigns `h-1`, `h-2`, ... to every `h2`-`h6` element (h1 excluded per D-02), and does nothing else — no text extraction, no slugification, no collision handling needed (ids are guaranteed unique by a monotonically increasing counter).

**When to use:** Replaces `rehype-slug` entirely in `astro.config.mjs`'s `markdown.rehypePlugins` array. Must run before `rehype-autolink-headings` in the same array (same ordering constraint that applied to `rehype-slug` previously — see Pitfall 1 below, carried forward from Phase 1's `01-RESEARCH.md`).

**Example (verified pattern — `unist-util-visit`'s `visit(tree, test, visitor)` signature confirmed against the installed 5.1.0 source in `node_modules/unist-util-visit`):**
```js
// src/lib/rehype-sequential-ids.mjs
import { visit } from 'unist-util-visit';

const HEADING_TAGS = new Set(['h2', 'h3', 'h4', 'h5', 'h6']); // h1 excluded per D-02

export function rehypeSequentialIds() {
  return (tree) => {
    let counter = 0;
    visit(tree, 'element', (node) => {
      if (!HEADING_TAGS.has(node.tagName)) return;
      counter += 1;
      node.properties = node.properties || {};
      node.properties.id = `h-${counter}`;
    });
  };
}
```

```js
// astro.config.mjs — updated rehypePlugins array
import { rehypeSequentialIds } from './src/lib/rehype-sequential-ids.mjs';
// ...
rehypePlugins: [
  rehypeKatex,
  rehypeSequentialIds,        // replaces rehypeSlug — MUST still run before autolink-headings
  [rehypeAutolinkHeadings, {
    behavior: 'prepend',
    content: h('span.heading-anchor', '#'),
    properties: { class: 'heading-anchor-link' },
  }],
],
```
Source basis: `unist-util-visit`'s 3-arg `visit(tree, test, visitor)` overload and hast `element` node shape (`node.tagName`, `node.properties`) — confirmed directly from the installed `@astrojs/markdown-remark`'s own `rehype-collect-headings.js`, which uses the identical `visit(tree, (node) => { if (node.type !== "element") return; ... })` shape in this exact codebase's `node_modules`.

### Pattern 2: Right sidebar data — reuse Astro's built-in `headings`, do not hand-roll extraction

**What:** `const { Content, headings } = await render(post)` already returns `headings: [{ depth, slug, text }]` once Pattern 1's plugin has run (verified directly from `node_modules/astro/dist/content/runtime.js` line 437: `headings: entry?.rendered?.metadata?.headings ?? []`, which is populated by `@astrojs/markdown-remark`'s `rehypeHeadingIds` — see Architecture Diagram above for exactly how the custom ids flow through).

**When to use:** In `src/pages/posts/[slug].astro`, filter `headings` to `depth === 2 || depth === 3` (per D-08) and build a nested `<ul>` — h3 entries nest under the preceding h2. Pass this filtered/nested list as a prop to `RightNavSidebar.astro`. Apply D-10 (hide if fewer than 2 headings) as a simple `headings.length < 2` check before rendering the component at all.

**Example:**
```astro
---
// src/pages/posts/[slug].astro
const { post } = Astro.props;
const { Content, headings } = await render(post);
const outlineHeadings = headings.filter((h) => h.depth === 2 || h.depth === 3);
---
<Layout title={post.data.title}>
  <div class="post-layout">
    <LeftNavSidebar currentSlug={post.data.slug} currentTags={post.data.tags} />
    <article>
      <h1>{post.data.title}</h1>
      <Content />
    </article>
    {outlineHeadings.length >= 2 && <RightNavSidebar headings={outlineHeadings} />}
  </div>
</Layout>
```

### Pattern 3: Left sidebar data — group posts by tag at build time

**What:** A plain `getCollection('posts')` query, grouped into a `Map<string, Post[]>` keyed by each post's first tag (or, if multi-tag chapter membership is desired, every tag the post has — the CONTEXT.md leaves ordering/grouping-nuance to Claude's discretion, D-04's only hard constraint is "dynamic off whatever tag values exist, no fixed taxonomy").

**When to use:** Recommend keying by `tags[0]` (a post's *first* listed tag = its primary chapter) rather than fanning a post into every tag it has — this avoids a post appearing in multiple chapters simultaneously in the site-wide ToC, which would be confusing given the "book chapters" mental model in D-03's framing ("the ToC is for the contents of everything I have posted... like chapters"). This is a Claude's Discretion judgment call, flag it to the user as an assumption if they push back once there are 3+ chapters.

**Example:**
```astro
---
// src/components/LeftNavSidebar.astro
import { getCollection } from 'astro:content';

interface Props {
  currentSlug: string;
  currentTags: string[];
}
const { currentSlug, currentTags } = Astro.props;

const posts = (await getCollection('posts', ({ data }) => !data.draft))
  .sort((a, b) => a.data.date.valueOf() - b.data.date.valueOf()); // chapter-internal order: oldest-first reads like book chapters

const chapters = new Map<string, typeof posts>();
for (const post of posts) {
  const chapterName = post.data.tags[0] ?? 'Uncategorized';
  if (!chapters.has(chapterName)) chapters.set(chapterName, []);
  chapters.get(chapterName)!.push(post);
}
const currentChapter = currentTags[0] ?? 'Uncategorized';
---
<nav class="left-nav" aria-label="Site contents">
  {[...chapters.entries()].map(([chapterName, chapterPosts]) => (
    <details open={chapterName === currentChapter}>
      <summary>{chapterName}</summary>
      <ul>
        {chapterPosts.map((post) => (
          <li>
            <a href={`/posts/${post.data.slug}/`} aria-current={post.data.slug === currentSlug ? 'page' : undefined}>
              {post.data.title}
            </a>
          </li>
        ))}
      </ul>
    </details>
  ))}
</nav>
```
Note: within-chapter post order (oldest-first vs newest-first) is not locked by CONTEXT.md — oldest-first is recommended here because a "book chapter" reads front-to-back, but this is a Claude's Discretion call and should be flagged as such to the user, not stated as settled.

### Pattern 4: Accordion — `<details>`/`<summary>` vs custom JS

**What/tradeoffs:**

| | `<details>`/`<summary>` | Custom JS + `localStorage` (ThemeToggle-style) |
|---|---|---|
| Dependency-free | Yes — zero JS | No — needs a small script, same shape as `ThemeToggle.astro` |
| Auto-expand current chapter on load | Trivial — `open` boolean attribute set server-side from `chapterName === currentChapter` | Same, but requires the script to run before/without flash, similar to the theme pre-paint script |
| State persists across page loads (e.g. "I manually expanded chapter X, keep it expanded on the next post") | No — `open` resets to server-rendered default on every navigation (static site, full page loads, no client router) | Yes, if written to persist to `localStorage` |
| Styling control (custom disclosure triangle icon, animation) | Partial — `::marker`/`::-webkit-details-marker` can be restyled, but the open/close transition is not natively animatable without extra JS (`details` has no built-in transition hook in the CSS spec as broadly supported today) | Full control |
| Matches "hand-built, not templated" aesthetic goal (D-03 of Phase 2 CONTEXT.md) | Yes — plain semantic HTML is very much in line with the project's existing zero-JS posture | Also fine, but adds a second small script alongside `ThemeToggle.astro`'s |

**Recommendation:** `<details>`/`<summary>` is the simpler default and is explicitly consistent with this project's "zero-JS-by-default, opt-in only where needed" philosophy (Phase 2 CONTEXT.md, Integration Points section) — since this is a *static* multi-page site (full navigations between posts, not an SPA), `localStorage`-persisted expand state would only matter within a single page view anyway, which is low value. Use custom JS only if per-session accordion state persistence across full page loads becomes an explicit user request later.

### Pattern 5: Scroll-spy via `IntersectionObserver`

**What:** Observe each heading element (or a thin sentinel positioned at each heading) with `rootMargin` shaped to trigger near the top of the viewport, toggle an `is-active` class on the matching right-sidebar `<a>`.

**When to use:** Right sidebar only (D-09: bold/accent text, no border/bar — pure CSS class toggle, no layout shift).

**Example (verified pattern shape against current community guidance — see Sources):**
```js
// inline script in RightNavSidebar.astro, same is:inline pattern as ThemeToggle.astro
const headingEls = [...document.querySelectorAll('article :is(h2, h3)[id]')];
const sidebarLinks = new Map(
  [...document.querySelectorAll('.right-nav a[href^="#"]')]
    .map((a) => [a.getAttribute('href').slice(1), a])
);

const observer = new IntersectionObserver(
  (entries) => {
    for (const entry of entries) {
      const link = sidebarLinks.get(entry.target.id);
      if (!link) continue;
      link.classList.toggle('is-active', entry.isIntersecting);
    }
  },
  {
    // Triggers when a heading crosses a thin band near the top of the
    // viewport, rather than requiring 100% visibility — the standard
    // "reading position" scroll-spy shape.
    rootMargin: '0px 0px -80% 0px',
    threshold: 0,
  }
);

for (const el of headingEls) observer.observe(el);
```
Caveat (MEDIUM confidence, community pattern not an official spec recommendation): with `rootMargin: '0px 0px -80% 0px'` it's possible for zero headings to be "active" at the very top of the page (before the first heading is reached) or for the intersection to briefly report multiple active entries during fast scrolls — both are cosmetic edge cases (worst case: no bolded item briefly, never a broken link) and don't need special-case handling for a launch.

### Pattern 6: 3-column CSS Grid layout, non-disruptive to the existing centered column

**What:** Wrap the existing `<article>` (or `<main>`'s children) in a new grid container with three named areas; the *existing* `.site-header, main { max-width: 68ch; margin: 0 auto }` rule stays completely untouched — it continues to center `<main>` itself. The grid is applied to a new inner wrapper, and its center column is given `max-width: none` so it doesn't re-constrain content that's already inside the 68ch `<main>`.

**When to use:** Only on post pages (D-07) — homepage/about are unaffected since they don't render the wrapper.

**Example:**
```css
/* nav-sidebars.css */
.post-layout {
  display: grid;
  grid-template-columns: 1fr min(68ch, 100%) 1fr;
  grid-template-areas: "left content right";
  column-gap: var(--space-xl);
  /* Deliberately NOT setting max-width/margin here — this container is
     allowed to span the full viewport width so the 1fr side columns have
     real margin space to occupy; only the middle column is width-capped. */
}
.post-layout > article { grid-area: content; }
.left-nav { grid-area: left; }
.right-nav { grid-area: right; }

@media (max-width: 900px) {
  .post-layout {
    grid-template-columns: 1fr;
    grid-template-areas: "content";
  }
  .left-nav { display: none; } /* shown only via mobile toggle, D-05 */
  .right-nav { display: none; } /* hidden entirely on mobile, D-11 */
}
```
This requires `<article>` to no longer inherit `main`'s `max-width: 68ch` directly — since `.post-layout` (the grid) becomes the flex/grid item that's centered by `main`'s existing rule, and the grid's middle column does the 68ch capping instead. This is the one small restructuring needed in `[slug].astro`: wrap the article (and new sidebars) in a `.post-layout` div, and `main`'s existing rule now centers *that div* at whatever width the grid computes (which will be wider than 68ch on desktop, to make room for the side columns) — meaning `main`'s own `max-width: 68ch` must be scoped to not apply on post pages, or `.post-layout` must escape it via `max-width: none` on itself combined with a wider constraint. Recommend the simplest fix: give `.post-layout` `max-width: calc(68ch + 2 * (var(--space-xl) + 16rem))` (approximate sidebar width budget) and `margin: 0 auto`, overriding `main`'s narrower 68ch specifically for pages that render this wrapper via a more specific selector (`main .post-layout { max-width: ...; margin: 0 auto; }` beats `main { max-width: 68ch }` on specificity without needing `!important`). Verify the exact numbers visually during implementation — this is a CSS layout detail, not a locked contract.

### Anti-Patterns to Avoid
- **Re-deriving heading text/slugs for the id scheme:** Don't build a plugin that extracts heading text and then discards it to produce `h-N` — that's doing (and paying the KaTeX-math-text-extraction cost of, see Pitfall 3) unnecessary work. Sequential ids need zero text extraction, only element position.
- **Hand-rolling a second heading-collector for the right sidebar:** Don't write a separate rehype/remark plugin or vfile.data export to capture headings for the sidebar — Astro's `render()` already returns `headings` for free once Pattern 1 is in place (see Architecture Diagram). Building a parallel extraction mechanism risks the two heading lists (DOM ids vs. sidebar data) drifting out of sync.
- **`scroll` event + manual `getBoundingClientRect()` polling for scroll-spy:** Superseded by `IntersectionObserver` — polling on every scroll event is measurably worse for main-thread performance and is the dated approach per current guidance (see Sources).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Heading id/slug generation | A custom slugification+collision-avoidance scheme (kebab-case, dedupe counters like `-1`, `-2` suffixes) | The sequential-counter plugin in Pattern 1 | Collision-prone text-slugging (what `rehype-slug`/`github-slugger` solve) is irrelevant once ids are purely position-based — there's no more complex problem to hand-roll here, the "simple" solution *is* the correct one |
| Extracting a post's heading tree for the sidebar | A second AST-walking plugin exporting heading data via `vfile.data` | Astro's built-in `render(post)` → `headings` (Pattern 2) | Already computed by Astro's own pipeline; a second exporter would duplicate logic and risk drift from the actual DOM ids |
| Scroll-position tracking | `requestAnimationFrame` + manual scroll-offset math | `IntersectionObserver` (Pattern 5) | Native browser API purpose-built for this exact problem, better performance characteristics, less code |

**Key insight:** Every "hard-sounding" piece of this phase (custom ids, heading extraction) collapses to a very small amount of code specifically *because* the numeric-id decision (D-01) sidesteps the parts of `rehype-slug`/`github-slugger` that are genuinely complex (text normalization, unicode handling, collision counters). Don't be tempted to add that complexity back in.

## Common Pitfalls

### Pitfall 1: Rehype plugin ordering (carried forward, still applies with the new plugin)
**What goes wrong:** `rehype-autolink-headings` runs and finds no `id` on heading nodes, producing anchors with empty `href="#"`.
**Why it happens:** Astro only auto-injects heading ids via its own internal `rehypeHeadingIds` step, which always runs **after** every plugin in `markdown.rehypePlugins` (verified directly from `@astrojs/markdown-remark`'s `index.js`: user rehype plugins load and run at lines 76-78, `rehypeHeadingIds` is appended at line 81, strictly after). If the new `rehypeSequentialIds` plugin (Pattern 1) is placed *after* `rehype-autolink-headings` in the array instead of before it, the same failure mode as Phase 1's original Pitfall 1 recurs.
**How to avoid:** Keep `rehypeSequentialIds` immediately before `rehypeAutolinkHeadings` in `astro.config.mjs`'s `rehypePlugins` array (same position `rehypeSlug` previously occupied).
**Warning signs:** Any built page's `.heading-anchor-link` has `href="#"` (empty fragment) instead of `href="#h-N"`.

### Pitfall 2: Astro's internal `headings` text extraction walks into KaTeX-rendered spans
**What goes wrong:** For any h2/h3 that contains inline math (`$...$`), the `text` field in Astro's `headings` array (used to render the sidebar link label) may include a garbled concatenation of KaTeX's dual-rendering output — KaTeX emits both a visually-hidden `.katex-mathml` tree (screen-reader-readable math annotation, closer to normal text) and a `.katex-html` tree (broken into many single-glyph `<span>`s for visual layout) inside the same heading. Astro's internal `rehypeHeadingIds` text-collector (verified from source: `node_modules/@astrojs/markdown-remark/dist/rehype-collect-headings.js`) visits **all descendant text nodes** without skipping either KaTeX subtree, so the extracted `text` field is likely to contain duplicated/interleaved fragments from both representations rather than a clean rendering of the math.
**Why it happens:** `rehypeKatex` runs before the id/heading-collection step in the pipeline (both the custom id plugin and Astro's internal collector), so by the time text is extracted, math has already been expanded into its full dual-representation HTML — there's no "plain math source text" node left to grab.
**How to avoid:** This only matters for headings that contain inline math (uncommon for section headings, but possible in this domain given the KaTeX-heavy subject matter). If a post's headings need math, test the actual rendered sidebar label for that specific post before treating it as done — don't assume `headings[i].text` is clean for math-containing headings. If it's garbled, the pragmatic fix is a small text-cleanup pass (e.g., strip anything that looks like KaTeX's duplicated raw-annotation text) applied only where the sidebar renders `text`, not by changing the id/pipeline logic.
**Warning signs:** A right-sidebar link for a heading with inline math shows repeated or nonsensical text.

### Pitfall 3: Anchor id stability across builds — confirmed non-issue, but verify the assumption in practice
**What goes wrong (hypothetical):** If plugin execution order in the unified pipeline weren't deterministic, or if headings were processed out of document order, `#h-N` values could shift between builds even without content changes, breaking the "shorter, stable" promise (D-01)'s entire point.
**Why this is NOT actually a risk here:** `unist-util-visit`'s tree walk is a deterministic, synchronous, depth-first traversal of the AST in document order — the same order the headings appear in the source Markdown, every time, for the same input file. There is no async/parallel execution or non-deterministic ordering anywhere in this pipeline (confirmed by reading both the custom plugin's own visit call and Astro's own internal `rehypeHeadingIds`, which uses the identical traversal pattern). IDs are stable across rebuilds for **unchanged files**.
**What DOES change ids (working as intended, per D-01's own accepted tradeoff):** Adding, removing, or reordering a heading within a post shifts every `h-N` after that point in the same post. This is explicitly the accepted tradeoff in D-01 ("editing a heading's wording never breaks a link" — but inserting/deleting/reordering headings still does, unlike text-slug ids which only break on *wording* changes to that specific heading). Make sure the planner's task descriptions don't overstate stability beyond what D-01 actually promises.
**Warning signs:** None expected in normal operation; only relevant if the pipeline is later parallelized (not currently the case, and not planned).

### Pitfall 4: Astro 7's Markdown processor override footgun (carried forward from Phase 1 research, still applies)
**What goes wrong:** Astro 7 replaced its default Markdown processor with a Rust-based one ("Sätteri"); `markdown.remarkPlugins`/`markdown.rehypePlugins` set as flat arrays under `markdown` may silently not execute if the project isn't explicitly using `@astrojs/markdown-remark`'s `unified()` processor wrapper.
**Why it doesn't affect this phase directly:** This project's `astro.config.mjs` already opts into the `unified()`-wrapped processor (confirmed in the file read for this research — `processor: unified({ remarkPlugins: [...], rehypePlugins: [...] })`), so this footgun was already solved in Phase 1 and remains solved as long as the new plugin is added to the *same* `unified({...})` block, not to a separate `markdown.rehypePlugins` key outside it.
**How to avoid:** Add `rehypeSequentialIds` inside the existing `processor: unified({ rehypePlugins: [...] })` array shown in Pattern 1's example — do not create a second, parallel `markdown.rehypePlugins` config key.
**Warning signs:** A successful `astro build` that doesn't actually apply the new ids (build succeeding proves nothing — this exact silent-failure mode was Phase 1's original Pitfall 2).

### Pitfall 5: Multiple inline scripts in `Layout.astro`/page components — load order
**What goes wrong:** The scroll-spy script (Pattern 5) queries `.right-nav a[href^="#"]` and heading elements — if it runs before those elements exist in the DOM (e.g. if placed in `<head>` like the theme pre-paint script), `querySelectorAll` returns an empty list and scroll-spy silently does nothing.
**Why it happens:** `ThemeToggle.astro`'s script is deliberately placed at the end of `<body>`-rendered markup (inside the component itself, not in `<head>`) specifically so `document.getElementById('theme-toggle')` finds the button — the Layout's *other* pre-paint theme script is the one exception that must run in `<head>` before paint, for a different reason (flash-of-wrong-theme prevention) that doesn't apply to scroll-spy.
**How to avoid:** Place the scroll-spy `<script is:inline>` inside `RightNavSidebar.astro` itself (same placement pattern as `ThemeToggle.astro`'s script relative to its own button), not in `Layout.astro`'s `<head>`. Since Astro components render in document order, by the time this script tag executes, the sidebar's own `<a>` elements and the post's heading elements are already in the DOM.
**Warning signs:** Scroll-spy classes never toggle; console shows no errors (silent empty-NodeList failure, not a thrown error).
