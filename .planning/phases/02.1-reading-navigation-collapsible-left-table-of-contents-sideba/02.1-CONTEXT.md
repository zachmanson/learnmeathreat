# Phase 02.1: Reading Navigation (ToC sidebar, on-this-page sidebar, shorter anchors) - Context

**Gathered:** 2026-09-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Adds a three-piece reading-navigation system to post pages: (1) a shorter, stable heading anchor scheme replacing today's text-derived slugs, (2) a left sidebar listing every post on the site grouped into chapters by tag, and (3) a right sidebar outlining the current post's own headings with scroll-spy highlighting. This is an inserted phase (jumped ahead of Phase 3 per user priority) — it touches post-page layout and the Markdown heading pipeline, not content, RSS/sitemap, or deployment. NAV-01 (v2, deferred) is being pulled forward and expanded; this phase does NOT build the standalone Series/Topics grouping page (GROW-01) — the left sidebar's chapter grouping is a narrower, page-embedded version of that idea, not the full page.

</domain>

<decisions>
## Implementation Decisions

### Anchor hash scheme
- **D-01:** Heading IDs switch from today's rehype-slug text-derived slugs (e.g. `#why-shors-algorithm-breaks-ecdsa`) to **sequential numeric IDs** (`#h-1`, `#h-2`, ...). Chosen for maximum stability — the ID is position-based, so editing a heading's wording later never breaks a previously shared link. Trade-off accepted: the ID isn't self-descriptive from the URL alone.
- **D-02:** Numbering covers **all headings except h1** (h1 is the post title, not a section), in document order — h2 and h3 share one sequence rather than having separate counters. This matches how both sidebars will need to walk the heading tree.

### Left sidebar — site-wide post navigation
- **D-03 (scope correction — important for downstream agents):** The left sidebar is **not** a per-page outline. It lists every post on the site, organized into chapters — it's the site's book-style table of contents. The right sidebar (below) is the per-page "on this page" outline. Do not conflate the two.
- **D-04:** Posts are grouped into chapters using their existing **freeform tag frontmatter** (`z.array(z.string())`, unchanged from Phase 1's D-04). Do **NOT** lock a fixed chapter/category enum in this phase. The user plans to tag their first posts under one chapter (e.g. "Bitcoin Fundamentals") and organically add more chapters as they write more posts — the sidebar must group dynamically off whatever tag values exist, not a hardcoded list.
- **D-05:** The left sidebar is **always visible on desktop** (above the ~900px breakpoint, see D-10), hidden behind a toggle control on mobile/tablet.
- **D-06:** Chapters are **accordion-style, individually collapsible/expandable**. The chapter containing the post currently being viewed starts **auto-expanded**; other chapters start collapsed.
- **D-07:** The left sidebar appears **only on individual post pages**, not on the homepage (which already lists all posts reverse-chronologically) or the About page.

### Right sidebar — on-this-page outline with scroll-spy
- **D-08:** Shows the current post's own headings, **h2 + h3 nested** (fuller outline than the left sidebar's post-level grouping — useful for scroll-spy granularity in long posts).
- **D-09:** The active/in-view section is highlighted with **bold/accent-color text only** — no border or indicator bar. Matches the existing minimal aesthetic (Phase 2's quiet accent-color usage), avoids introducing new visual weight.
- **D-10:** The right sidebar **hides itself entirely** on posts with fewer than 2 headings (avoids showing a near-empty or single-item box).
- **D-11:** On mobile/narrow screens, the right sidebar is **hidden entirely** — no toggle (unlike the left sidebar). Rationale: avoids two competing toggle controls fighting for space on narrow screens.

### Overall page layout
- **D-12:** On desktop, both sidebars **flank the existing centered content column** — the post content stays at its current 68ch width and page-centered position (`src/styles/global.css` `.site-header, main { max-width: 68ch; margin: 0 auto; }`); sidebars occupy the margin space outside it. This is a smaller change than shifting the whole three-column block off-center, and preserves Phase 1/2's established centered-column reading experience.
- **D-13:** The breakpoint that collapses to the current single-column mobile layout (hiding both sidebars, per D-05/D-11) is **~900px (tablet and below)** — sidebars only appear on genuinely wide desktop viewports where there's real margin space to use.

### Claude's Discretion
- Exact visual treatment of the left-sidebar mobile toggle (icon choice, placement) — no specific mechanic was locked, only that it exists and is hidden-by-default on mobile (consistent with the existing `ThemeToggle.astro` pattern of a simple icon control in the header).
- Exact chapter/tag ordering within the left sidebar (e.g. alphabetical vs. first-post-date order) when multiple chapters exist — not enough chapters exist yet to have a strong preference; use a sensible default (likely order of first appearance or alphabetical) and let the user redirect if it looks wrong once there's real content.
- Implementation mechanism for generating `#h-N` IDs (custom rehype plugin replacing/supplementing `rehype-slug`) — technical approach, not a user-facing decision.
- Exact smooth-scroll vs. instant-jump behavior when clicking a right-sidebar link — not discussed; default to smooth-scroll unless it conflicts with reduced-motion preferences.

</decisions>

### Established Patterns
- `.site-header, main { max-width: 68ch; margin: 0 auto; }` in `global.css` — the single centered-column layout this phase must extend to a 3-column layout on wide screens (D-12) without breaking the existing narrow/mobile single-column behavior.
- `astro.config.mjs`'s markdown processor pipeline (`unified({ remarkPlugins, rehypePlugins })`) — the established, documented place to add/modify heading-ID generation (D-01/D-02) and to extract heading data for both sidebars (likely via a custom rehype plugin that also exports a heading tree per post).
- Zero-JS-by-default posture (per Phase 2 CONTEXT.md) — this phase's scroll-spy (right sidebar, D-09) and accordion (left sidebar, D-06) both require client JS, following the same "small amount of vanilla JS, opt-in only where needed" pattern already established by `ThemeToggle.astro`'s theme-init script.

### Integration Points
- `src/pages/posts/[slug].astro` — Where both sidebars get rendered around the post `<Content />`; currently a simple `<article>` wrapper inside `<Layout>`.
- `src/layouts/Layout.astro` — Site-wide layout; likely needs a way to conditionally render the left/right sidebars only on post pages (per D-07) while leaving homepage/about untouched.
- Content Collections `getCollection('posts', ...)` — Already used in `[slug].astro` and presumably `index.astro`; the left sidebar's full post-and-chapter list will need a similar collection query, filtered/grouped by tag.
