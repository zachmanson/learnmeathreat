## Summary

This phase extends the site's existing hand-rolled `unified()` markdown pipeline (`astro.config.mjs`) — it does **not** need MDX. The project already proved (Phase 1/02.1) that arbitrary remark/rehype plugins compose cleanly via `markdown.processor: unified({ remarkPlugins, rehypePlugins })`, and that custom transform plugins following the `unist-util-visit` pattern (see `src/lib/rehype-sequential-ids.mjs`) are the established way to add project-specific behavior. All four new primitives fit this same model:

- **Figures**: a `remark-directive` leaf directive (`::figure[caption]{src="..." alt="..."}`) transformed by a small custom remark plugin into a `<figure><img/><figcaption>Figure N: ...</figcaption></figure>` hast tree, with the SVG-vs-raster dark-mode-invert decision made automatically from the file extension.
- **Citations**: `rehype-citation` (built on citation-js) reads a root-level `references.bib`, recognizes `[@key]`/`@key` syntax in the rendered hast tree, and auto-inserts a per-page bibliography. A tiny custom remark plugin (same shape as `rehype-sequential-ids.mjs`) rewrites the user's `\cite{key}` text into `[@key]` before `rehype-citation` runs.
- **Callouts and definitions**: both use the exact same mechanism — `remark-directive` for the `:::name ... :::` fenced syntax, plus one shared custom remark plugin that maps directive names (`note`/`warning`/`tip`/`definition`) to styled `<div class="callout callout-{name}">` hast output. This is one implementation serving two content requirements (D-09/D-11), not two.

**The DSGN-01 conflict (D-04)** is real and mechanical: `tests/theming.test.mjs` test 22 (line 302) does a blanket `!/<img[\s>]/i.test(html)` regex across every built page. Any `<Figure>` output will fail it as written. The fix is to scope the check — strip/allow `<figure class="content-figure">...</figure>` blocks before applying the existing regex, and add a *stronger* replacement assertion (no `<img>` at all on non-post pages; on post pages, every `<img>` must be inside `<article>`) so the guard's actual intent (no hero/marketing imagery) is preserved and arguably tightened, not weakened.

**Primary recommendation:** Install `remark-directive` + `rehype-citation` only (no MDX, no `citation-js` as a direct dependency — it ships bundled inside `rehype-citation`'s own dependency tree under `@citation-js/*` scoped packages). Write three small custom remark plugins (cite-translate, directive-to-hast for figures, directive-to-hast for callouts/definitions) following the existing `rehype-sequential-ids.mjs` style. Rewrite `tests/theming.test.mjs` test 22 rather than deleting it.

### Pattern 1: Directive → hast transform (figures AND callouts/definitions share this shape)

**What:** A single custom remark plugin, run immediately after `remark-directive`, that inspects `containerDirective`/`leafDirective` node names and assigns `node.data.hName`/`node.data.hProperties` so `remark-rehype` knows how to render them as plain HTML elements.

**When to use:** Any time you need "custom Markdown syntax → specific HTML output" without MDX. This is the officially documented `remark-directive` pattern (its own README example is literally the "note/tip/warning" admonition case).

**Example (verified pattern — source: `github.com/remarkjs/remark-directive` README, adapted to this project's callout/definition names):**
```javascript
// src/lib/remark-directive-to-hast.mjs
import { visit } from 'unist-util-visit';
import { h } from 'hastscript';

const CALLOUT_NAMES = new Set(['note', 'warning', 'tip', 'definition']);

export function remarkDirectiveToHast() {
  return (tree) => {
    let figureCounter = 0; // reset per-file: this function body runs once
                            // per markdown file (same scoping rule as
                            // rehype-sequential-ids.mjs's `counter`).

    visit(tree, (node) => {
      if (node.type !== 'containerDirective' && node.type !== 'leafDirective') return;

      if (CALLOUT_NAMES.has(node.name)) {
        const data = node.data || (node.data = {});
        const hast = h('div', { class: `callout callout-${node.name}` });
        data.hName = hast.tagName;
        data.hProperties = hast.properties;
        return;
      }

      if (node.name === 'figure' && node.type === 'leafDirective') {
        figureCounter += 1;
        const { src, alt = '' } = node.attributes || {};
        const isSvg = /\.svg$/i.test(src || '');
        const data = node.data || (node.data = {});
        data.hName = 'figure';
        data.hProperties = { class: 'content-figure' };
        // Replace the directive's own children with explicit <img> + <figcaption>
        // (label text built from the directive's bracketed label, mdast children).
        node.children = [
          { type: 'element', data: { hName: 'img', hProperties: {
              src, alt, class: isSvg ? 'invertible' : undefined, loading: 'lazy',
            } }, children: [] },
          { type: 'element', data: { hName: 'figcaption' },
            children: [{ type: 'text', value: `Figure ${figureCounter}: ` }, ...node.children] },
        ];
      }
    });
  };
}
```
**Authoring syntax this enables:**
```markdown
::figure[A transparent-background SVG diagram]{src="/images/shor-circuit.svg" alt="Shor's algorithm circuit diagram"}

:::note
This is standard content inside a note box.
:::

:::definition
**Superposition** — a quantum state that is a linear combination of multiple basis states.
:::
```

### Pattern 2: `\cite{key}` translation + `rehype-citation` wiring

**What:** A tiny remark plugin (same file-size and complexity as `rehype-sequential-ids.mjs`) that rewrites literal `\cite{key}` text into `[@key]` text *before* `rehype-citation` (a rehype plugin) scans the hast tree for citation syntax.

**Why this ordering works:** `remark-directive`/`remark-math`-style extensions and this plugin all run in the remark (mdast) phase; `rehype-citation` explicitly documents running "after remark-math/rehype-katex conversion" in the rehype phase [CITED: github.com/timlrx/rehype-citation]. By the time `rehype-citation` runs, the hast tree already contains plain text nodes reading `[@key]`, which is exactly the syntax `rehype-citation` natively recognizes.

**Example:**
```javascript
// src/lib/remark-cite-translate.mjs
import { visit } from 'unist-util-visit';

const CITE_PATTERN = /\\cite\{([^}]+)\}/g;

export function remarkCiteTranslate() {
  return (tree) => {
    visit(tree, 'text', (node) => {
      if (CITE_PATTERN.test(node.value)) {
        CITE_PATTERN.lastIndex = 0; // reset global regex state before reuse
        node.value = node.value.replace(CITE_PATTERN, '[@$1]');
      }
    });
  };
}
```
Note: visiting only `type: 'text'` mdast nodes naturally skips `inlineCode` nodes — a literal `` `\cite{foo}` `` in a code span will NOT be translated, which is almost certainly the desired behavior (matches how `$math$` inside code spans is also left alone by `remark-math`).

**astro.config.mjs wiring (full recommended pipeline):**
```javascript

import rehypeCitation from 'rehype-citation';

// ...existing imports (remarkMath, rehypeKatex, rehypeSequentialIds, rehypeAutolinkHeadings, h)

    // ...existing shikiConfig...
```

### Anti-Patterns to Avoid

- **Adding `@astrojs/mdx` for this phase:** Solves a problem D-02/D-09/D-11 don't have (JSX-like component invocation inside content). Adds a second content file extension, a second Content Collections glob pattern, and a real Astro integration to maintain — directly against this project's established "don't hand-roll a web-dev exercise" posture. Use directives instead (Pattern 1).
- **Declaring the figure/callout counter outside the returned transformer function:** If `let figureCounter = 0` is placed in the plugin's outer factory scope (the part that runs once when `.use()` is called) instead of inside the function returned to `unified` (the part invoked once per file), figure numbers will keep incrementing across every post in a single `astro build` run instead of resetting per post. The existing `rehype-sequential-ids.mjs` already gets this right — copy its exact scoping, don't "simplify" it.
- **Hand-rolling bibliography formatting or a custom `[key]` → `<a>` linker:** Directly contradicts D-07. `rehype-citation` already handles CSL-correct author-date/numeric formatting, hyperlinking citations to bibliography entries, and locale support — a hand-rolled version would need to reimplement CSL processing to match citation-style correctness.
- **Using `remark-definition-list`'s `Term\n: Definition` syntax for D-11:** No explicit end marker, contradicting the user's explicit requirement for controllable start/stop. Use the directive mechanism already needed for callouts instead.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Parsing `:::name ... :::` fenced block syntax out of raw Markdown text | A regex-based Markdown preprocessor that splits on `:::` lines before handing text to the Markdown parser | `remark-directive` | Correctly handles nested Markdown inside the block (bold, links, inline math, other directives), blank-line/indentation edge cases, and both container (`:::`) and leaf (`::`) forms — a regex preprocessor would silently mishandle nested content or code fences containing literal `:::` text. |
| CSL-correct citation formatting (author-date, numeric, note styles) and bibliography sorting | A hand-rolled `[key]` → footnote-number formatter reading raw BibTeX fields | `rehype-citation` (citeproc-js/citation-js under the hood) | Citation Style Language formatting has genuinely complex rules (author name disambiguation, "et al." thresholds, sort order, locale-specific punctuation) that citeproc-js already implements correctly; a hand-rolled version is a multi-week rabbit hole for a personal blog. |
| BibTeX file parsing (`.bib` format edge cases: nested braces, `@string` macros, multi-line fields) | A custom BibTeX tokenizer | `rehype-citation`'s bundled `@citation-js/plugin-bibtex` | BibTeX's grammar has real edge cases (brace-balanced field values, `@string` abbreviation expansion) that a from-scratch parser would get wrong on the first slightly-unusual `.bib` entry. |

**Key insight:** Every "don't hand-roll" item above is a parsing/formatting problem with a long tail of edge cases that only show up once real content is written — exactly the kind of thing this phase exists to get right *before* real posts are authored (per the phase's own stated purpose).

## Common Pitfalls

### Pitfall 1: DSGN-01 test 22 will fail the moment a `<Figure>` is used, if not rewritten first
**What goes wrong:** `tests/theming.test.mjs` line 302-312 does `assert.ok(!/<img[\s>]/i.test(html), ...)` across every page in `PAGES` (currently `index.html`, `about/index.html`, one published post). The instant any post uses the new figure directive, `npm test` fails on this exact assertion — not a new bug, but an *expected*, planned conflict per D-04.
**Why it happens:** The original Phase 2 test was written when zero images existed anywhere in the site and correctly encoded "DSGN-01 = no images" as its literal, unscoped interpretation.
**How to avoid:** Rewrite test 22 (not delete it) to scope the check. Concretely:
```javascript
test('22. (DSGN-01 guard) no marketing/hero <img> outside authored content figures', () => {
  for (const page of PAGES) {
    const html = readDistFile(page);
    const withoutContentFigures = html.replace(
      /<figure class="content-figure">[\s\S]*?<\/figure>/g,
      ''
    );
    assert.ok(
      !/<img[\s>]/i.test(withoutContentFigures),
      `${page} contains an <img> tag outside an authored content figure - DSGN-01 forbids stock/hero imagery`
    );
  }
  const css = readDistCss();
  assert.ok(!/background-image\s*:/i.test(css), 'built CSS contains a background-image declaration - DSGN-01 forbids stock/hero imagery');
});

test('22b. (DSGN-01 guard) non-post pages never contain any <img> tag', () => {
  for (const page of ['index.html', 'about/index.html']) {
    const html = readDistFile(page);
    assert.ok(!/<img[\s>]/i.test(html), `${page} contains an <img> tag - only post content may contain figures`);
  }
});
```
**Warning signs:** `npm test` failing on test 22 the first time a post with a figure is built is expected and correct if this rewrite hasn't landed yet — do not "fix" it by weakening the regex to match anything, and do not delete the test.

### Pitfall 2: `.prose` class referenced in CONTEXT.md does not exist in the actual codebase
**What goes wrong:** `02.2-CONTEXT.md`'s canonical-refs and code-context sections repeatedly describe scoping new CSS to "`.prose` content" and mention a `src/styles/prose.css` file "scoped to `.prose`." Grepping the actual `src/` tree for `class="prose"` or `.prose` as a selector returns **zero matches**. `prose.css` is a real file, but its selectors (`h2, h3`, `pre`, `code`, `.katex`, `.astro-code`) are unscoped/global — they are not nested under a `.prose` wrapper class anywhere.
**Why it happens:** The actual content wrapper on post pages is a plain `<article>` element (see `src/pages/posts/[slug].astro`), not an element carrying a `.prose` class. CONTEXT.md's wording appears to be describing an intended/assumed convention that was never implemented as a literal CSS class.
**How to avoid:** When scoping new figure/callout/definition CSS (and when writing the DSGN-01 test rewrite's "must be inside post content" check), target the actual `<article>` element or the new `.content-figure`/`.callout` classes directly — do not write a `.prose` selector expecting it to match anything.
**Warning signs:** New CSS rules like `.prose .content-figure { ... }` that silently do nothing because `.prose` never appears in rendered HTML.

### Pitfall 3: Figure/callout numbering state must be scoped per-file, not per-build
**What goes wrong:** If a plugin author declares a counter variable outside the function unified actually calls per-file (i.e., in the plugin factory's outer closure rather than inside the returned transformer), the counter persists and keeps incrementing across every markdown file processed in a single `astro build` run, producing "Figure 7" on a post's very first figure instead of "Figure 1."
**Why it happens:** `unified().use(plugin)` calls the plugin factory function once per pipeline construction, not once per file; only the *returned* transformer function runs once per file.
**How to avoid:** Copy the existing, already-correct scoping in `rehype-sequential-ids.mjs` exactly: `let counter = 0` must be the first line **inside** the arrow function returned by the exported plugin function (see Pattern 1's code example above, which follows this rule).
**Warning signs:** Figure numbers that don't start at 1 on posts other than the first one built.

### Pitfall 4: Uncertain whether `rehype-citation`'s auto-inserted bibliography interacts with `rehypeSequentialIds`/the on-this-page sidebar
**What goes wrong:** If `rehype-citation`'s default bibliography output includes its own heading element (e.g., an `<h2>Bibliography</h2>` or similar), it will land in the hast tree *before* `rehypeSequentialIds` runs (per the recommended pipeline order above) and will therefore receive an auto-numbered `#h-N` id and show up in `[slug].astro`'s `outlineHeadings` filter (which selects all `depth === 2 || depth === 3` headings for the 02.1-built "on this page" right sidebar).
**Why it happens:** This phase's plugin ordering was chosen based on `rehype-citation`'s documented recommendation ("after remark-math/rehype-katex"), but its exact default output structure (does it wrap the reference list in a heading, a plain `<div>`, or something else — and at what heading depth if any) was not verified against the live rendered HTML in this research session — LOW confidence, needs a build-time check.
**How to avoid:** During implementation, build a test post with one citation, inspect the actual `dist/` HTML output for the bibliography's exact markup (heading level, wrapper element, `id` if any), and decide deliberately whether "References" should appear in the on-this-page outline (arguably desirable — it's a page section) or be excluded (if `rehypeSequentialIds`/the outline filter would otherwise produce a confusing result). Only reorder `rehypeCitation` relative to `rehypeSequentialIds` if the default output causes a real problem — do not preemptively re-order without evidence.
**Warning signs:** A stray "h-N" heading in test output or the rendered right sidebar showing a heading with no visible corresponding post-body heading.

### Pitfall 5: `remark-directive`'s fenced containers need blank lines around the fence, like fenced code blocks
**What goes wrong:** Authors used to writing `:::note` immediately followed by content on the very next line (no blank line) may get a directive that fails to parse as a container, or that swallows/mis-nests surrounding paragraphs.
**Why it happens:** `remark-directive`, like standard CommonMark fenced code blocks, expects the block-level container syntax to be separated from surrounding block content by blank lines to be recognized as its own block-level construct — this is standard commonmark-family container-block behavior, not a quirk unique to this plugin. [ASSUMED — general commonmark-family behavior, not independently verified against remark-directive's own test suite in this session; verify with a real multi-paragraph note block at implementation time.]
**How to avoid:** Document the required blank-line-before/blank-line-after convention wherever authoring syntax is documented for the user (e.g., in a project CLAUDE.md note or a comment in a seed post), and add at least one automated test asserting a `:::note` containing a full paragraph (not just one line) renders correctly.
**Warning signs:** A callout box that renders empty, or that merges with a following paragraph into a single block.

## Code Examples

Verified patterns from official sources:

### remark-directive → hast transform (official README example)
```javascript
// Source: https://github.com/remarkjs/remark-directive (README "Example: rendering directives" section, verified via WebFetch 2026-09-05)
import { visit } from 'unist-util-visit';
import { h } from 'hastscript';

function myRemarkPlugin() {
  return function (tree) {
    visit(tree, function (node) {
      if (
        node.type === 'containerDirective' ||
        node.type === 'leafDirective' ||
        node.type === 'textDirective'
      ) {
        const data = node.data || (node.data = {});
        const hast = h(node.name, node.attributes || {});
        data.hName = hast.tagName;
        data.hProperties = hast.properties;
      }
    });
  };
}
```
Pipeline order requirement, per the same README: `unified().use(remarkParse).use(remarkDirective).use(myRemarkPlugin).use(remarkRehype)` — the custom transform MUST run after `remarkDirective` and before the (Astro-internal) remark-rehype conversion.
