# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — plain Astro `.astro` components + semantic HTML (unchanged from Phase 1) |
| Icon library | none — theme toggle uses two inline SVG glyphs (sun/moon) hand-drawn or sourced from a single permissively-licensed icon (e.g. Lucide's `sun`/`moon` paths, inlined as static SVG, not a JS icon library dependency) |
| Font | **Body/nav/meta:** unchanged system-ui stack from Phase 1. **Headings (h1-h3) only:** IBM Plex Mono, weight 600, self-hosted `.woff2` (per CONTEXT.md D-01/D-02/D-03) |

**Why no shadcn/component library:** Same rationale as Phase 1 (see `01-UI-SPEC.md`) — plain Astro static site, zero-JS-by-default, no React/Next/Vite in the stack. This phase adds the site's *first* client JS (theme toggle: read/write `localStorage`, toggle a `data-theme` attribute) but this does not change the "no component framework" posture — it stays vanilla `<script>`, not a library.

**Why IBM Plex Mono, headings only, weight 600 only:** Locked by CONTEXT.md D-01/D-02. Self-hosted to avoid an external network request (Google Fonts CDN rejected per project's "no unnecessary third-party dependency" posture). One weight only because headings in this project never need a secondary weight (no bold-within-heading convention exists) — matches Phase 1's 2-weight-total system (400 body regular via system-ui, 600 headings). Font files must be added under `src/assets/fonts/` (or `public/fonts/`) and declared via `@font-face` in `global.css` with `font-display: swap` to avoid invisible-text-during-load; subset to Latin if using a subsetting tool, otherwise ship the full static woff2 (do not add a build dependency solely for subsetting — not worth the complexity for a single-author blog's font-weight budget).

## Spacing Scale

Declared values (must be multiples of 4) — unchanged from Phase 1, this phase does not introduce new spacing roles:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Tag chip inline padding, gap between icon-less inline elements |
| sm | 8px | Gap between post meta items (date · tags), nav link gaps, gap between nav links and theme toggle |
| md | 16px | Default paragraph/element spacing within post body |
| lg | 24px | Space between post list items on homepage |
| xl | 32px | Space between nav bar and page content, section padding |
| 2xl | 48px | Space above/below page title |
| 3xl | 64px | Top-level page margin |

Exceptions: **Theme toggle button** gets a minimum 44×44px tap target (icon button, no visible label) even though its icon glyph itself is small — this is the standard mobile touch-target accessibility minimum and does not affect the icon's visual size (icon renders at ~20px within the 44px hit area, using padding to pad out the click/tap zone). This is the single sanctioned exception to the 8-point scale, consistent with the template's stated allowance for "icon-only touch targets at 44px."

## Typography

Base type scale (sizes/weights/line-heights) is **unchanged from Phase 1** — this phase changes only the `font-family` applied to the Heading and Display roles, not the scale itself (per CONTEXT.md canonical_refs: "only the font-family and color values change, not the scale system").

| Role | Size | Weight | Line Height | Font family |
|------|------|--------|-------------|-------------|
| Body | 18px | 400 (regular) | 1.6 | system-ui stack (unchanged) |
| Label (meta: date, tags, nav) / Code | 14px | 400 (regular) | 1.4 (1.5 for code blocks) | system-ui stack (unchanged) / `ui-monospace` code stack (unchanged) |
| Heading (h2/h3 in post body) | 24px | 600 (semibold) | 1.25 | **IBM Plex Mono** (new — was system-ui in Phase 1) |
| Display (page title: post title, "About", homepage intro, site title `h1`) | 32px | 600 (semibold) | 1.2 | **IBM Plex Mono** (new — was system-ui in Phase 1) |

Only 2 weights total remain declared (400 system-ui body, 600 IBM Plex Mono headings) and 4 sizes total — the accent font swap does not add a 3rd weight or 5th size, keeping the minimal token budget from Phase 1 intact.

**Visual anchor (unchanged from Phase 1, now reinforced by the accent font):** Post title (Display, 32px/600, IBM Plex Mono) is the primary focal point on both the homepage list and individual post pages. Because IBM Plex Mono is visually distinct from the system-ui body font, the heading/body contrast becomes more pronounced than Phase 1's same-family weight-only contrast — this is the intended effect (DSGN-02: "distinct... accent font, visually separate from body text").

**Guardrail against "code font gimmick" (per CONTEXT.md D-03):** Do not apply IBM Plex Mono to: the nav links, the site title in the header bar (`.site-title` — this stays system-ui per D-02, only in-content `h1`/page titles get the mono treatment), body prose, meta text (date/tags), buttons, or the theme toggle. Confining it strictly to h1-h3 elements is what keeps it reading as "quiet accent" rather than "this is a dev blog, look at the terminal font."

Math (KaTeX) continues to render in its own required math font per Phase 1's CONT-02 rationale — unaffected by this phase's heading font change.

## Color

Phase 1 shipped light-only. This phase adds a **dark palette** derived from the same token names (per CONTEXT.md: "add a dark equivalent of each existing color token, don't introduce new roles"). Both palettes below use the *same 5 role names* (`--bg`, `--surface`, `--accent`, `--text`, `--muted`) — dark mode is a value swap via `[data-theme="dark"]`, not a new system.

### Light (unchanged from Phase 1 — default / initial paint before JS runs)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) — `--bg` | `#FFFFFF` | Page background |
| Secondary (30%) — `--surface` | `#F4F4F5` | Code block background, tag chip background, subtle nav/footer separation |
| Accent (10%) — `--accent` | `#1D4ED8` | Links only: nav links, post title link, heading anchor `#` on hover, in-body links |
| Text — `--text` | `#18181B` | Body text |
| Muted — `--muted` | `#71717A` | Meta text (date/tags), nav link color |
| Destructive | not applicable | No destructive actions in this project (read-only content site) |

### Dark (new this phase)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) — `--bg` | `#09090B` (zinc-950, near-black not pure black) | Page background |
| Secondary (30%) — `--surface` | `#18181B` (zinc-900) | Code block background, tag chip background, subtle nav/footer separation |
| Accent (10%) — `--accent` | `#60A5FA` (blue-400, lightened from light mode's blue-700 for sufficient contrast on near-black) | Links only — same reserved elements as light mode |
| Text — `--text` | `#FAFAFA` (zinc-50) | Body text |
| Muted — `--muted` | `#A1A1AA` (zinc-400) | Meta text (date/tags), nav link color |
| Destructive | not applicable | Unchanged |

**Accent reserved for (both themes):** nav links (Home/About), post title link on the homepage list, in-body prose links, and the heading anchor `#` glyph (shown only on hover/focus). The theme toggle icon itself uses `--text`/`--muted`, NOT `--accent` — it is a utility control, not a link, and should not compete visually with the 10% accent budget.

**Contrast requirement:** `--accent` (`#60A5FA`) on `--bg` (`#09090B`) must meet WCAG AA for normal text (4.5:1) since it's used for inline prose links — verify at implementation time; if the chosen blue-400 falls short, shift toward blue-300 (`#93C5FD`) rather than introducing a 6th color role.

**KaTeX dark-mode requirement (explicit, per CONTEXT.md canonical_refs):** KaTeX's default rendered output does not automatically inherit the page's dark text color for every glyph/rule element (fraction bars, radical signs, etc. use `border-color`/`background-color`, not always `color`). Add a `[data-theme="dark"] .katex { color: var(--text); }` override and manually verify (visually, in a real dark-mode render) that fraction bars, square-root lines, and matrix brackets are visible against `--bg` — do not assume `color: inherit` alone fixes every KaTeX-rendered element.

**Shiki dark-mode requirement (explicit):** Phase 1 pinned a single `theme: 'github-light'` in `astro.config.mjs`. This phase must switch to Shiki's dual-theme config (`shikiConfig.themes: { light: 'github-light', dark: 'github-dark' }` with `defaultColor: false`), which emits both light and dark color variables per token in the build output. Pair this with CSS scoped to `[data-theme="dark"]` that selects the dark variant (per Shiki/Astro's documented dual-theme CSS-variable pattern) — do not attempt to re-run Shiki per-theme at request time (there is no request time; this is a static build).

## Interaction Contract (Phase-2-specific, beyond template defaults)

- **Theme toggle mechanics (DSGN-03):** Icon-based sun/moon toggle button placed in `.site-header nav`, alongside the Home/About links (per CONTEXT.md Claude's Discretion). On first visit (no stored preference), theme follows the OS-level `prefers-color-scheme` media query. Once the user clicks the toggle, the explicit choice is persisted to `localStorage` and takes precedence over OS preference on all future visits. The theme is applied via a `data-theme="light|dark"` attribute on `<html>`. **Flash-of-wrong-theme prevention is mandatory:** the theme-detection/application script must run as a small inline `<script>` in `<head>`, before first paint — not as a deferred/module script — so the correct `data-theme` is set before any CSS paints. This is the only architecturally load-bearing piece of this phase; get it right or dark-mode users see a light flash on every page load.
- **Dark palette application:** All 5 color roles (`--bg`, `--surface`, `--accent`, `--text`, `--muted`) get dark values inside a `[data-theme="dark"] { ... }` override block in `global.css`, using the same custom-property names as Phase 1's `:root` block — no parallel/duplicate styling system, no new token names.
- **KaTeX/Shiki dark legibility (DSGN-03):** See explicit requirements in the Color section above. Both must be manually visually verified in dark mode before this phase is considered done — a math-heavy post and a post with a code block should both be checked in both themes.
- **Mobile nav (DSGN-04):** Reuse Phase 1's existing `.site-header { flex-wrap: wrap; gap: var(--space-sm); }` baseline. The theme toggle button joins the nav's flex-wrap group — no hamburger menu, no JS-driven collapse/expand, per CONTEXT.md Claude's Discretion ("no JS collapse unless it visibly breaks"). Verify at narrow widths (375px reference) that site title, Home, About, and the toggle all wrap cleanly without horizontal overflow or overlapping text.
- **Heading accent font scope (DSGN-02):** IBM Plex Mono applies ONLY to `h1`, `h2`, `h3` elements rendered from post/page content (post titles, "About" title, in-body subheadings). It does NOT apply to `.site-title` (header wordmark), nav links, the theme toggle, meta text, or body prose — see Typography section guardrail above.
- **No new destructive/error/empty states introduced this phase** — this is a pure visual/theming phase per CONTEXT.md's phase boundary ("does not touch content, routing, or the Markdown pipeline").
